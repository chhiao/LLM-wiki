# 驗證與評估

## 為什麼重要
- 任務驗證問題約占 MAS 失敗的 24% [S4]。
- 驗證者常只做表面檢查，應改成多層、檢查高層目標的驗證 [S4]。

## 做法
| 做法 | 說明 | 來源 |
|---|---|---|
| 程式化檢查 | prompt chaining 中間步驟可加程式檢查 | [S1] |
| Evaluator-optimizer | 一個生成、一個評估回饋，反覆改進 | [S1] |
| 看結果不看步驟 | 正確路徑有很多種，評估結果是否正確、過程是否合理 | [S2] |
| 小量起步 | 一開始約 20 個真實問題就夠 | [S2] |
| LLM-as-judge | 單一 LLM 依 rubric 評事實、引用、完整度、來源品質、工具效率 | [S2] |
| 人工測試 | 抓出自動檢查漏掉的邊緣案例與來源偏誤 | [S2] |
| 多層 guardrails | 不靠單一檢查；高風險動作前交給人類 | [S6] |

## 對本作業的啟示 [推論]
簡報產生流程也是一個小型 agent 系統，所以照 MAST 的建議設計了多層檢查（大綱關卡 → 內容關卡 → 呈現關卡），而且每一關檢查的是「教學目標有沒有達成」這種高層目標，而不只是「HTML 能不能開」。
